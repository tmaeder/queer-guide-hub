# Email platform benchmark and Queer Guide integration requirements

Reviewed 2026-10-20. This extends the integrated email implementation; it does not replace its scope. The user requires Cloudflare only and asks for capabilities comparable to Klaviyo, ActiveCampaign and Mailchimp throughout Queer Guide.

## Assessment

The current branch implements a transactional delivery and consent foundation, not a peer of these established marketing platforms. Relevant email capabilities must be implemented and verified individually. An editor, an outbox, or a long feature list is not evidence of lifecycle automation, effective deliverability, attribution or personalization.

Cloudflare explicitly supports transactional email only. Consequently, marketing and newsletter dispatch are blocked. This is an actual functional gap against all three benchmarks, not a configuration option. No worker, SMTP relay, queue, or self-built campaign engine changes the delivery service's documented restriction. Keep the Cloudflare-only requirement; do not route promotional mail through the transactional service. [Cloudflare FAQ](https://developers.cloudflare.com/email-service/reference/faq/)

The comparison below concerns relevant email, customer-data and automation functions. SMS, WhatsApp, advertising management and a generic CRM are adjacent product lines, not silently added delivery channels. Vendor documentation establishes advertised capability, not a hands-on quality, scale or inbox-placement comparison. Availability varies by product and plan.

## Architecture required beyond the current foundation

1. **Event and identity spine.** Versioned first-party event contracts, transactionally emitted by authoritative server writes or verified webhooks. Maintain operational events separately from consented behavioral events. Do not copy the entire `user_events` or `notifications.metadata` JSON into an email customer profile.
2. **Shared policy evaluator.** Every campaign and flow step checks identity, channel/topic permission, suppression, message purpose, provider capability, quiet hours, frequency budget, content visibility and whether its source action is still current. A UI toggle cannot bypass this evaluator.
3. **Segment engine.** Bounded typed predicates over approved traits and consented events, with nested logic, real database counts and inclusion/exclusion explanations. No arbitrary SQL or sensitive-field interpolation from an admin JSON rule.
4. **Journey runtime.** Immutable published versions and persisted contact runs/step executions. Claim due work with leases; process event replays idempotently. Wait states survive deployment; exits and membership checks run again before every message. Pausing or editing a definition never silently rewrites a running version.
5. **Campaign/content/experiment system.** Snapshot approved content, persist an audience and experiment assignment, and revalidate recipients at send time. Published blocks resolve only current public entities. Support localization, plain text, previews and declared fallback behavior.
6. **Measurement and operations.** Stitch delivery and app outcomes using first-party correlation IDs. Hold out a real control group when measuring lift. Exclude bots and label unknown attribution. Provide contact/flow timelines, reasoned skips, operational metrics and retention/erasure.

## Release gates for a defensible parity claim

- Every domain above has an owner, a tested event producer, a documented consent/message-purpose mapping and either a working journey or an explicitly justified exclusion.
- Each capability row has executable acceptance tests plus production evidence where a local fixture cannot prove it.
- End-to-end journeys include registration → welcome → activation exit; consent → confirmation → newsletter eligibility → withdrawal; RSVP → schedule change → cancel; group join → leave; trip reschedule → stale reminder cancellation; verified payment → acknowledgement; account deletion → canceled pending work.
- A replay or concurrent worker produces one logical step and one provider submission. Opt-out, suppression and goal completion between enrollment and dispatch prevent an ineligible step.
- Experiments produce stable assignments, reported sample sizes and honest inconclusive results; a click cannot be presented as a booking or donation.
- Controlled sender authentication, real inbox rendering/delivery, event subscriptions, missing credentials, quota exhaustion, expired leases and DLQ recovery are verified. A green build cannot establish deliverability parity.
- Marketing sending remains a failed release gate while the Cloudflare restriction applies. The original goal must not be marked complete merely because all local foundation tests pass.

## Implementation order

The benchmark has prompted shared escaped rendering, required-variable/URL validation, generic private-message digests, and atomic confirmation-token/consent/outbox persistence. Account erasure/export, explicit recipient ownership, immediate pre-dispatch checks, versioned dynamic audiences, contact timelines and operational event producers for accounts/usernames/RSVPs/groups/trips are implemented and locally tested. A bounded durable journey runtime now adds publication windows, pinned versions, waits, live branches, re-entry, source exits, leases, pause/resume/cancel, queue linkage and receipt-gated welcome steps. Its action catalog deliberately remains limited to account welcome; it is not a full automation product. DM digests now use independent email opt-in, DST-aware quiet hours, an atomic daily activity reservation, current primary mailbox and live unread/unmuted membership checks. Group post mentions and verified trip invitations now join this policy through authoritative source capture, independent explicit opt-in, original-membership and current-source/block checks, generic previews and the shared activity budget. Trip invitations also have a signed-in accept/decline flow, role guards, admission limits and sharing/Plans controls. Other activity producers still require explicit purpose/preferences and source-visibility rules. Next extend the policy to those transactional domain adapters, then the journey UI, campaign binding/approvals, content blocks, experiments and reporting. Keep all remaining acceptance gates visible; provider-held data lifecycle, full production schema compatibility, real delivery and measured capacity remain unproven. Marketing sending remains blocked.

Sources were checked using the built-in browser after the connected Firecrawl account reported insufficient credits. No vendor account was connected, and no comparative production deliverability or scale experiment has been performed.
