# Activity email delivery policy

Optional activity adapters now cover `dm_digest` and verified `group_mention` post events; see `email-group-mentions.md` for the latter. Essential account/service mail continues through its existing eligibility checks, independent of these activity settings. Marketing/newsletter delivery remains blocked by Cloudflare's transactional-only capability. This is not yet a global policy for every transactional producer.

## Member settings and API

`email-subscriptions` GET requires Auth and returns both `subscription` and `delivery_preferences`. POST with `action: "delivery_preferences"` accepts `dm_digest_enabled`, `timezone`, `quiet_hours_enabled`, integer `quiet_start`/`quiet_end` (0–23) and optimistic `version`. The endpoint derives the user from verified Auth; it never accepts a caller-selected owner. A stale version returns 409, invalid values return 400. The UI requires reload after a conflicting save. Saving activity settings never subscribes a member to newsletter topics.

No existing account is automatically opted into digest email, including accounts with `dm_push_enabled=true`. That flag continues to control push independently. Missing preferences mean email digest disabled, quiet hours off, `Etc/UTC`, 22:00–08:00 as the initial configurable interval, version zero. The first explicit save creates version one and an immutable change-history snapshot. PostgreSQL validates named time zones against its installed time-zone database. Account settings expose the separate controls alongside newsletter preferences.

## Eligibility and provider boundary

`dm_digest_candidates` returns generic counts without sender names or message previews. It requires explicit digest opt-in, current Auth mailbox, an existing profile, an enabled account, available quiet hours, no current-day digest marker, no plaintext mailbox suppression, and at least one qualifying unread conversation. Qualifying notifications must be unread DM activity at least two hours old, with a current, unmuted conversation participant whose last-read time precedes the activity. Missing conversation/membership or a read/muted conversation is ineligible. This adapter reuses the product's authoritative notifications/participants; broader relationship/block visibility verification remains a production integration gate.

`email_activity_message_reason` applies the same current preference, primary mailbox and source checks to queued rows. Claim cancels permanently ineligible queued digests as suppressed; a live processing lease stays intact so a receipt from a request already in flight can still be persisted. Expired processing leases are cancelled on the next claim. Quiet hours and a used daily allowance hold rows without spending attempts. Dispatch re-reads the source and preference after claim, before the authenticated Worker request. A row without explicit account ownership cannot pass. Digest snapshots expire within 24 hours; late mail does not persist indefinitely behind a quiet window. Turning settings back on does not revive a previously suppressed logical message.

Quiet intervals include their start and exclude their end, and may cross midnight. Equal start/end is rejected when quiet hours are enabled. Conversion uses `AT TIME ZONE`, so skipped spring hours and both repeated autumn hours follow the member's actual local clock. This does not change the scheduler's daily UTC identity or guarantee delivery at the first minute after quiet hours.

Before a digest can cross the provider boundary, `email_dispatch_authorize` reserves a unique `(user_id, UTC day)` in `email_activity_reservations`. Authorization uses the same account lock as preference saves and erasure, so erasure cannot leave a newly inserted reservation behind. Competing rows cannot both reserve the same day, including overlapping transactions. The same outbox identity can retry against its original Worker Durable Object receipt. A timeout or uncertain provider result keeps its reservation because a message might already have been submitted. This conservative allowance measures possible submissions, not confirmed deliveries. It is not a rolling 24-hour or local-calendar-day cap; submissions on either side of UTC midnight can be close together. Group post mentions now join this budget; other activity domains still need explicit adapters.

Database authorization narrows the race between opt-out/read/mute/erasure and network submission; it cannot recall mail or atomically lock a member's settings across an external provider call. No provider request is issued during local contract tests.

## Privacy and verification

Preferences, change history and reservations have RLS enabled and service-only grants; public/member roles cannot read other accounts or invoke policy RPCs. Account exports include owned preferences/history/reservations, and existing erasure/anonymization barriers delete them transactionally. Auth deletion also cascades them. Preference history and reservation retention periods still require production policy, alongside the existing outbox and Durable Object retention requirements.

The policy SQL suite covers defaults, validation, optimistic conflicts, overnight and daytime quiet hours, spring/autumn DST, unread/mute/read/membership changes, current mailbox, opt-out after claim, daily reservation/retry behavior, essential-mail independence, export, erasure and permissions. The concurrency script holds one authorization uncommitted while another competes, verifies only one daily reservation succeeds, and verifies replay of the winning identity remains eligible. UI tests cover explicit opt-in without newsletter enrollment, independent unsubscribe, quiet-hour validation, failed-load recovery and conflicting saves. Fixtures supply only required product columns; full production schema and actual delivery remain rollout checks.

Local verification on 2026-10-20: all six migrations applied to a fresh isolated PostgreSQL database; all six SQL suites and all three real overlapping-transaction cases passed. Fifteen shared backend contracts and six member-settings UI tests passed. Changed endpoints passed Deno checking, changed UI passed ESLint, the existing typecheck ratchet reported no new errors (698 existing errors versus baseline 782), and the production frontend build passed. The security advisor reported no issues on the isolated fixture database. Desktop/mobile settings fixtures at 1280/390 pixels had no horizontal overflow or browser errors. No production migrations, deployment or real mail were performed.
