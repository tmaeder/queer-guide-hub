# Queer Guide

LGBTQ+ travel & community platform at queer.guide

## Commands

| Task | Command |
|------|---------|
| Install | `npm install` |
| Dev | `npm run dev` (port 8080) |

| Test | `npm test` |

**Typecheck is a baseline ratchet.** `npm run typecheck` runs `scripts/typecheck-ratchet.mjs` → real `tsc -p tsconfig.app.json --noEmit`, compared against `scripts/typecheck-baseline.json`; it fails only on errors NEW per (file, TS-code). ~1.4k pre-existing errors are recorded there (a large share are Supabase client type-inference `SelectQueryError` unions, not live bugs). Fix errors rather than re-baselining; after fixing, run `npm run typecheck:baseline` to lock the improvement in. `npm run typecheck:functions` is a separate **zero-tolerance** gate (`tsconfig.functions.json`) covering `functions/` — the Cloudflare Pages edge middleware, which `tsconfig.app.json` (`"include": ["src"]`) never saw; it starts and must stay at 0 errors. Until 2026-07-29 `typecheck` was bare `tsc --noEmit` against the solution-style root tsconfig (`"files": []` + `references`) — with no `-b` that compiles **zero** files and always exits 0, so the CI gate was vacuously green for its whole life. Never "fix" errors by loosening `tsconfig.app.json`.

The scraper has its own `package.json` under `scraper/` — `cd scraper && npm install`, then `npm test` etc. there. Workers each from their own directory: `wrangler dev` / `wrangler deploy`.

**Backend:** Supabase (PostgreSQL 17.4, Auth, Storage, Edge Functions), Cloudflare Pages + Workers, GitHub Actions (scraper cron)

**A human "approve" in the triage inbox did nothing, for as long as the inbox has existed (fixed 2026-08-22):** every approve path — `triage_action('staging','approve')`, `triage_bulk_approve_high_conf`, the Import Hub's `ingestion-review-api`, the dedup-resolution RPCs — writes `ingestion_staging.review_status='approved'`, but **every downstream stage gates on a different column**, `ai_validation_status`: `pipeline-deduplicate`, `pipeline-review-gate`, `marketplace-relevance`, `enrichment-driver` and all six `commit_*_staging_batch` require it to read `approved`, and **the only writer of that value is `pipeline-validate`**. So once validate returned `needs_review` — for a venue a single `W_NO_COORDS` is enough — the row was invisible to dedup, to the review gate and to commit forever, and the queue collected human decisions and discarded them. Measured on prod: **14 events stranded since 2026-07-13 (40 days)** plus 25 eventfrog venues. What is NOT wrong is commit, which already accepts `review_status IN ('auto','approved')` — `ai_validation_status` was the only door shut, which is why hand-flipping that one column drained the 25 venues. **The promotion lives in a BEFORE UPDATE trigger (`trg_staging_human_approval_clears_validation`), not in the approve RPC**, because there are at least four writers of `review_status='approved'` and patching one leaves three; it stamps `ai_validation_result.human_override` (from/by/at) so the override is visible on the row without erasing the validator's errors/warnings/quality. It promotes `pending` and `needs_review` **only** — a validator hard rejection is never silently overridden — and the new sentinel `pipeline_hygiene_stats().stranded_human_approved` is deliberately **wider** than the trigger (`ai_validation_status IS DISTINCT FROM 'approved'`), so any shape the trigger refuses to clear (a hard rejection marked approved, or a writer that INSERTs `approved` instead of UPDATEing it) hard-fails `check-pipeline-health.mjs` at **one row, no baseline allowance**, instead of being auto-cleared. It is its own key rather than part of `stale_pending_by_entity` because **those thresholds are why this hid for 40 days**: 14 rows sit far under a 3,500-row warn floor. The one-shot repair **publishes every stranded row, past-dated events included.** A first draft dispositioned them by their own date — a row approved 40 days ago was approved as an *upcoming* event — and that was **rejected as a rule for this corpus**: `events` deliberately holds ~36.5k past events from the Wayback import, so a past date is not a defect here and "already happened" is not grounds to discard a human approval. (The 14 were all `gaycities` pride/festival imports flagged `W_PRIDE_TIME_WINDOW` + `W_PRIDE_NOT_SATURDAY` + `W_NO_GEO` — 3 warnings ≥ `warnReview` — and 5 had already ended.) Undated rows are promoted rather than pre-rejected too: commit RAISEs `event_missing_start_date` and the batch handler writes that on the row, so the commit path dispositions them with a real reason instead of the migration guessing. Migration `20260916120000`; guarded by `src/lib/__tests__/stagingHumanApproval.test.ts`.

**Auto-pause erases its own evidence, and took the whole ingest engine down for 40 hours (2026-08-25):** `workflow_dispatcher_1min` is the ONLY consumer of the `pipeline_steps` queue, i.e. the sole stepper for every DAG. A burst of `workflow-dispatcher` HTTP 500s on 2026-08-23 13:28 tripped `auto_pause_threshold=3`, setting `enabled=false`; pg_cron kept firing for another ~14h (auto-pause does not unschedule), the job kept SUCCEEDING, and then the nightly `automation_cron_sync` (`10 5 * * *` → `sync_automations_to_cron(true)`) branch (b) unscheduled every disabled row at **2026-08-24 05:10**. Measured effect: `pipeline_runs` went 84 completed/0 failed on 08-23 → **0 completed/70 reaped** on 08-25, all seven ingestion pipelines with every node still `pending`; news_articles/day 141→**0**, events 232→7, venues 1718→2; 181 undrained `pgmq.q_pipeline_steps` messages. **Push notifications died with it** — the same sweep took nine automations. `reap_stuck_pipeline_runs()` was reporting the outage, not causing it. **The trap is that the pause deletes the proof it happened:** the success branch of `admin_automation_runs_after_finish()` resets `consecutive_failures=0` and `last_run_status='success'` but **never re-enables**, so a falsely-paused row ends up reading exactly like a deliberate human retirement. The only durable record is `summary.auto_paused` on the historical run row. **`workflow_runs` says the work COMPLETED and that is not evidence** — `enqueue_workflow()` posts the `action:'start'` leg directly over HTTP and gets a 200; the per-node `'continue'` steps are what the dispatcher drives, and only those stopped (`pipeline-executor` runs 274→6). Always confirm on `pipeline_runs`/`node_states`, never on a start-leg 200. **This was the THIRD occurrence** (`search_reindex_drain` 2026-08-22, `admin_automation_reap` 2026-08-16) and the sentinel written after the second one was hardcoded to `slug=eq.search_reindex_drain` while its own comment described the mechanism verbatim — one slug out of ~240. `scripts/check-pipeline-health.mjs` now checks **every** slug and separates the two cases: auto-paused **and still failing** is legitimate and only warns (`marketplace_variant_backfill` sits at 288 real failures and must stay off), while auto-paused **then recovered** (`consecutive_failures=0 AND last_run_status='success' AND enabled=false`) hard-fails. That rule found an 8th victim the by-hand restore had missed, `marketplace_taxonomy_backfill`, with 21,613 listings still unclassified. **Recovery is not just `enabled=true`:** an `action->>'type'='rpc'` row carries **no `action.command`**, so `sync_automations_to_cron()` branch (d) structurally CANNOT reschedule it (all rpc automations are scheduled by their own migration) — re-enabling leaves it on-but-unscheduled, and the cron must be recreated from that migration. **Always read the `recreated` list the sync returns instead of assuming it worked.**

**Cron automations record their own runs (2026-09-10):** until `20260910163700`, **142 of the 144 enabled `action->>'type'='cron'` rows had `last_run_at = NULL` and zero `admin_automation_runs`** — nothing on the pg_cron → `net.http_post` path wrote back, so `consecutive_failures` never moved and the auto-pause net from `20260523340000` **could not fire for any of them**. Not theoretical: `city_safety_backfill` failed six consecutive nights (2026-08-11…16) on an `ON CONFLICT` with no matching constraint, and nothing anywhere said so. **The 144 are THREE families and each needs a different truth source** — 74 call `net.http_post` in the command text, 20 call `enqueue_workflow()` which posts internally, 50 are pure synchronous SQL. `cron.job_run_details` was populated all along (7-day retention) and is exact for family C, but for A and B it reports `succeeded` the instant the request is **enqueued** — so projecting it wholesale manufactures a false green that *resets* `consecutive_failures` on every failing run, which is worse than the blank column it replaces. Hence two mechanisms: **dispatch truth** `admin_automation_project_cron_runs()` (records a raised exception as an error run for every family — for a tracked job that is the ONLY evidence, since the pg_cron transaction rolls the bookkeeping back with it — and records successes for family C only, sampled hourly, because four registered jobs fire every minute and per-execution rows would add ~10k/day to a disk-constrained DB); **response truth** `admin_automation_reap_runs()` (*/5), which joins `net._http_response` **BY REQUEST ID**. A and B get `admin_automation_run_begin('<slug>')` prefixed onto the cron command and their posts re-pointed at `public.automation_http_post`, a signature-identical shim that files each request id against the open run through the transaction-local GUC `app.automation_run_id`. **The registry stays canonical** — `action.command` keeps the original readable SQL, the wrapped form exists only in pg_cron, is derived by `admin_automation_effective_command()` and applied by `sync_automations_to_cron()`'s new command-drift branch, so one reconciler pass converted all 95 and a later migration re-scheduling the raw command is re-wrapped automatically. **Traps:** (1) **a trigger on `net.http_request_queue` is the design this wants to be and is NOT available** — the table is owned by `supabase_admin` and postgres is not a member (`42501 must be owner of relation`); don't re-attempt it. (2) **Never resolve a pg_net response by recency or URL** — `net._http_response` is shared by every caller on the instance and **has no url column at all**, and urls aren't unique across jobs anyway (`city_factual_backfill` and `city_factual_sparql` post to the same one); a "newest row" reaper already mis-read a `translate-i18n-batch` response as the adult-links one during the #2795 verification, which is why `request_id` is the **PRIMARY KEY** of `admin_automation_run_requests` — the mistake is unspellable, not merely discouraged. (3) The rewrite is a **token substitution, never an argument-list parse**: the 74 commands include a `DO` block, a `WITH … WHERE EXISTS` and two that post twice in one statement, and every expression-level wrap breaks on all three. (4) **A run with zero requests is a no-op SUCCESS, not a failure** — several commands post conditionally, and the run row's own survival proves its transaction committed. (4b) **A pg_net `timed_out` response is `partial`, NOT `error`, and never touches the counter** — it means pg_net gave up client-side while the edge function kept running, so it is absence of evidence, not evidence of failure. Measured on the first live pass: 2 of 41 requests, both jobs whose registered command omits `timeout_milliseconds` and so inherits pg_net's **5s default**; counting them would have auto-paused `workflow_dispatcher_1min` (every minute, core) within three minutes. The cost is that a target which merely *hangs* never auto-pauses, so `admin_automation_tracking_gaps().unverifiable_automations` (≥3 runs in 24h, all unverifiable) is what stops such a job reading as healthy — the fix is per job: raise the registered `timeout_milliseconds` until the response fits, and the hang becomes a countable failure. (5) `net._http_response` retention is **~6h measured**, so the reaper's `*/5` is load-bearing; a stalled reaper loses the evidence permanently rather than catching up. (6) Wrapping a command whose helper still calls `net.http_post` directly yields a false green, so only helpers listed in `admin_automation_tracked_callers` (proof of patching, not a wish list) may be wrapped, and `admin_automation_tracking_gaps().untracked_http_dispatchers` hard-fails CI on a new one. The projector's cursor starts at the current head, **forward-only**: backfilling seven days would auto-pause everything already failing, which is a decision to take deliberately rather than a migration side effect. Auto-pause sets `enabled=false`; the cron itself stops at the next `sync_automations_to_cron(true)` (nightly 05:10), so a paused job can still fire for up to a day. **Its first day in production found two faults in itself, both fixed 2026-08-16.** (7) **There was ALREADY a projector and I did not find it before shipping a second one.** `run_cron_failure_sweep` (hourly, since ~2026-07-31) records the same `cron.job_run_details` failures; the two dedupe against different keys (`summary->>'runid'` vs the `cron_runid` column) so neither can see the other's rows — measured, 9 runids carried two error rows each. Duplicate audit rows would be cosmetic, except that widening the auto-pause trigger to `BEFORE INSERT OR UPDATE` means an already-finished row now increments, so **two writers increment twice per failure and `auto_pause_threshold=3` trips after two real failures** — which is how `admin_automation_reap`, the layer everything else depends on, auto-paused itself. `20260816113024` makes them **disjoint by construction** rather than cross-deduping: the projector owns every job with a registry row, the sweep keeps only crons with none (those land `automation_id IS NULL`, so they can never reach the counter). `consecutive_failures` cannot be repaired by arithmetic after double-counting — recompute it as *terminal error runs newer than the most recent terminal non-error run*, which is the same quantity the trigger accumulates. (8) **Two `*/5` jobs that both write `admin_automations` will deadlock, and these did** — the projector locks rows in automation order, the reaper in open-run order (indirectly, via the auto-pause trigger on the parent row): four deadlocks in the first three hours. `20260816113041` gives both a shared `pg_try_advisory_xact_lock(hashtext('admin_automation_tracking'))` via thin `*_tick()` wrappers (try, not blocking — a skipped tick is free, a queued pg_cron worker turns a stall into a pile-up) and offsets the reaper to `2-59/5` so the lock is a backstop rather than the mechanism. They stay **two jobs**: merging them into one transaction also kills the deadlock but couples the reaper's unrecoverable ~6h evidence window to the projector's recoverable 7-day one. The wrappers exist so the reviewed function bodies are not restated to insert two lines at the top.

Those urls are re-requested at `width=512` with the crop dropped and the ANSWER is measured (`imageSize` on the returned bytes), because Shopify never upscales past the original and rodeoh.com's asset really is 32px. **Declared size is a claim; pixel dimensions are the evidence.** Two guards earn their place: `og:image` is never a source (on a shop it is a hero or product photo, which in a 56px plate reads as a corrupted logo), and the host check runs against the url we ASKED for, not where we landed — cellblock13.net 301s to timoteo.net and declares Timoteo's logo, which judged by the final url would publish a sibling brand's wordmark as CellBlock 13's. White/inverted variants are demoted (not dropped) because **the plate is paper in BOTH themes**: `--color-logo-plate` is a literal in `@theme`, not `var(--card)`, since a merchant logo is a transparent PNG drawn for a light ground and on a dark card most of the catalogue would render as nothing. Demotion is not enough on its own: **9 of the 118 mirrored marks contain no dark pixel at all** (7 of the first 80, then 2 more that logo.dev returned — detected with no intervention, which is the point of measuring rather than listing) (Automic Gold ×2, Good Boy Underwear, Jeuf, Nattaup, Provocateur, SUPAWEAR) — the site's only logo IS the white one — and those render as an empty square. **No CSS treatment fixes this**; all three were built and compared side by side, and a blurred edge barely rescues a white mark, a hard 1px outline rescues it but fattens every thin dark wordmark into a smear (Vilain Garçon, gc2b), and an ink plate is perfect for white marks and erases every dark one. So polarity is MEASURED per row: `_shared/png-luminance.ts` decodes the bytes at mirror time and stores `marketplace_brands.logo_on_ink` in the same UPDATE as the url it describes. The metric is the **fraction of visible pixels that are dark**, not mean luminance — a dark mark on its own white field (RUFSKIN) has a high mean and is perfectly legible. The 2% floor sits in a measured gap: the corpus is bimodal with nothing between 0.000 and 0.027. **The file name is not evidence** — SUPAWEAR's asset is `…-logo-white.png` but Automic Gold's is `Automic_GOLD_logo-_left_align` and is equally invisible. PNG-only is not a gap: the failure needs transparency, JPEG cannot be transparent, and an unreadable image stays on paper because a wrong ink plate erases a dark wordmark completely. **The ink plate must be a mode-independent LITERAL, and `bg-foreground` is the trap** — it reads as "ink" and is ink in light mode, so it passes review and every class-name unit test, but in dark mode `--foreground` IS paper: the plate rendered paper-on-paper and the white mark vanished again, in exactly the mode the fix existed to survive. Caught only on prod (`class` said `bg-foreground`, computed `background-color` said `rgb(250,250,245)`). Hence `--color-logo-plate-ink`, declared in `@theme` alongside `--color-logo-plate` and for the same reason both are literals: polarity belongs to the ARTWORK, not the theme — the same rule that makes `--track-ring` ink in both modes. A test asserts neither plate carries a theme token. Result: 82 brands, **9.3% of brands but 60% of listings** — the directory is ordered by listing count, so the logo-dense rows are the ones a reader meets. `BrandMark` renders the monogram ALWAYS and layers the logo over it, and **also needs an `onError` that hides the img** — Chrome paints its torn-page glyph for a failed image even with `alt=""`, so the monogram underneath is not on its own enough (found live). Driver `scripts/data-quality/backfill-brand-logos.mjs`; `enrich-logos` gained `table:'marketplace_brands'`. **Local dev cannot verify this visually**: a Cloudflare rule on the zone answers `img.queer.guide` with `error code: 1011` for any Referer that is not `https://queer.guide/` — localhost AND pages.dev both 403, so a broken logo plate on `npm run dev` is the WAF, not the data.

**Three OSM operational traps, all found by WATCHING PROD, none by any test** (42 unit tests and a 4/4 e2e passed throughout). (1) **A busy upstream is not our failure.** The per-venue path had the rule right — 429/5xx and remark-bearing 200s are "ask again later" — then the RUN recorded `status='error'` when every mirror came back busy, feeding `consecutive_failures` against `auto_pause_threshold=3`. (2) **A single-shot control probe condemns a flapping mirror** — `overpass-api.de` was measured answering 504 then 200 to the identical query seconds apart. (3) **Probing every endpoint after finding a healthy one burns the wall clock**: measured, overpass-api.de answered in 1.1s while kumi.systems hung to timeout, spending ~120s of a 240s budget before the first venue. **Two process lessons from the same session.** (a) **`scripts/check-migration-versions.mjs` without `SUPABASE_ACCESS_TOKEN` cannot see the real ceiling.** Local max read `20261103100000`; the true applied max was `20261127100000`, and two successive renumbers (`20261106*`, `20261111*`) both sorted BELOW it. ### SPA routing on Cloudflare Pages (2026-08-01)

**Three things here are load-bearing and `scripts/check-pages-routing.mjs` fails the build if any of them changes: no SPA catch-all in `public/_redirects`, no `public/404.html`, and `public/_routes.json` present.** With no `404.html` in the output, Pages' built-in fallback serves `index.html` (200) for any unmatched path and leaves static assets alone. That is the only shape that works; every alternative was measured against the real rule engine (`wrangler pages dev`) and fails:

- `/*  /index.html  200` — **silently dropped.** Pages strips `.html`/`/index` from rewrite targets, so the rule re-enters itself and the parser discards it as an infinite loop. Everything then fell through to `404.html`: `/help`, `/city/:slug` and every sitemap 404'd site-wide. Wrangler printed the warning on *every* deploy for months and nobody read it.
- `/*  /  200` — parses, but **200-rewrites outrank static-asset serving**, so `/robots.txt`, `/build-id.txt` and every hashed `/assets/**.{js,css}` are served the SPA HTML. The homepage rendered completely unstyled. (#2469, reverted in #2473.)
- `/section/*  /index.html  200` — same infinite-loop drop. `/section  /index.html  200` — 308-redirects instead of rewriting. **No rewrite whose target is `/index.html` can ever work here.**
- Status `404` is not expressible: Pages accepts only 200/301/302/303/307/308. Four `/assets/* /404.html 404` guards lived in the file for months and were rejected by the parser on every deploy.

`public/_routes.json` is shipped explicitly rather than left to wrangler. Without it wrangler generates the routing config and reads it back inside a bare `catch {}` (the `routesOutputPath` branch of `pages deploy`), which can upload the Functions bundle with no routes at all and no warning. The explicit file takes the validated branch and logs `✨ Uploading _routes.json` on every deploy, so the config is provably applied. **This was tried as a fix for the dead-Functions fault below and did NOT fix it** — keep the file (it removes a real silent-failure path), but do not mistake it for the cause.

### Poisoned BROWSER cache for /assets/* — per-user, no purge or deploy can fix it (2026-08-08)

`_headers` stamps `/assets/*` `immutable, max-age=31536000` **on whatever Pages serves under that path** — verified live: a nonexistent hashed URL returns the SPA shell `200 text/html` with the immutable header; mid-deploy it can be a 404. A browser that fetches a chunk during a deploy window caches that failure **for a year, in the user's own HTTP cache** — a third variant after the CDN-PoP and CORS-variant poisonings, and the only one no purge, redeploy or hash rotation can reach. A document reload (including `?__fresh=`) cannot fix it: the fresh document re-imports the same hashed URL through the poisoned cache (measured on a real user's Chrome after the #2621 deploy — 8 chunks pinned at 404, guard fired every reload, page blank forever). The ONLY escape is a per-URL `fetch(url, {cache:'reload'})`, which bypasses **and rewrites** the entry. Three layers now do this: (1) `public/sw.js` retries any suspect `/assets/*`/`/fonts/*` response with `cache:'reload'` and serves the fresh copy transparently — controlled clients never even see the failure; (2) the inline boot guard (`index.html` + the middleware-injected copy in `functions/_lib/boot-guard.ts`, kept byte-identical by `src/test/__tests__/bootGuardSync.test.ts`) heals every known asset URL **before** its `?__fresh=` reload and allows **two** gated attempts (attempt 1 can land while the window is still propagating); (3) `src/main.tsx` heals failed URLs quietly on post-boot `vite:preloadError` so a poisoned lazy-route chunk can't brick that route on every future visit (`src/utils/assetHeal.ts`). A `_headers` per-status override is not expressible, and `/assets/*` must stay excluded from Functions (`_routes.json`, quota) — client-side healing is the only available layer.

**Read wrangler's parser output.** It reports dropped `_redirects` rules — and says nothing at all about unrouted Functions — on a deploy that otherwise exits 0 and prints "Deployment complete".

**A bad `_redirects` rule outlives its revert — it poisons the CDN.** The `/  200` window above lasted ~13 minutes, but Pages answered `/assets/css/index-*.css` with `index.html` during it and `public/_headers` stamps `/assets/*` `immutable, max-age=31536000`, so Cloudflare cached the SPA shell **under the stylesheet URL for a year**. The site rendered completely unstyled for hours after the revert deployed, across three clean deploys, because reverting config does not evict a cached object and the content hash never moved. Two things to know: **(1) it is per-colo** — `smoke-pages.sh` passed from the CI runner while the same script failed from Zurich, so a green deploy proves one colo is clean and nothing more; **(2) the escape is a purge or a new URL, never a redeploy.** `expect_asset_type` in `scripts/smoke-pages.sh` now tells the two causes apart (plain URL wrong + `?cb=` right ⇒ poisoned cache; both wrong ⇒ origin broken). ### Stale SPA documents on the APEX — SOLVED 2026-08-04/05, and it was OUR code

**The conclusion this section carried for a day ("Cloudflare-side; needs support") was wrong, and so was its instruction not to look in `functions/_middleware.ts` — that is exactly where the bug was.** Fixed in #2591 + #2593; re-verified on prod 2026-08-10: `/events`, `/venues`, `/news` and `/cities` all return **no `age` and no `x-robots-tag`**, which is the signature's absence.

Two defects, both ours:

1. **`env.ASSETS.fetch('/')` used a key that never changes across deploys**, so a stale shell answered `/` for days and every deep route served a document referencing a chunk later deploys had deleted. Now keyed by `env.CF_PAGES_COMMIT_SHA` (`functions/_middleware.ts:256`), falling back to the bare path — a 404 there would kill EVERY deep route.
2. **`headers: indexResponse.headers` copied the subrequest's headers wholesale**, publishing its `age`, `accept-ranges` and an `x-robots-tag: noindex` that nothing in this repo sets — to Googlebot, on real indexable pages. Now only `content-type` plus an explicit `cache-control`.

**The leaked `age` fabricated the evidence for the wrong theory.** `age: 130273` beside `cf-cache-status: DYNAMIC` is a contradiction, and that contradiction became the central clue about a CDN cache that never held the object — which is what bought purge-by-URL, `purge_everything`, a dashboard purge, and **Always Online switched off on the zone**. Rules earned: **never copy a subrequest's headers onto a public response**, and **any internal fetch with a constant key is a staleness bomb** — if the body is build-specific, the key must be. Also: a CSP nonce compared across two requests always mismatches (it is per-request), so compare within ONE request (`curl -sD h.txt URL -o b.html`) — the cross-request comparison is what produced the false "the guard is CSP-blocked" finding below.

Round 2 (#2593) found two more of ours: the stale shell arrives as **`200`, not `404`**, so the SPA-fallback branch gated on 404 never ran — the discriminator is that our Functions build HTML per request and never emit `age`, so `status === 200 && has('age')` means a cached static object (`functions/_middleware.ts:244`). And **Cloudflare Rocket Loader re-executes inline scripts without their nonce**, so the nonce-CSP blocked the injected boot guard — the one script whose only job is recovering a blank page was itself disabled. `bootGuardTag()` now emits `data-cfasync="false"`; `vite.config.ts` had it at *build* time, but the guard is injected at *request* time. **`wrangler pages dev` has no Rocket Loader, so this class is invisible locally.**

**The old advice here was "do not fix this in `_middleware.ts` — sourcing the shell from `env.ASSETS.fetch('/')` is the wrong layer."** It was exactly backwards: that call *was* the bug (see the top of this section). Only its caveat survived and is still live — replacing a 200 body must not clobber the Function-generated HTML that `functions/news/[slug].ts` and friends legitimately return from `next()`, which is why the 200-branch is gated on the `age` header and was verified against `/news/<slug>` keeping its own `<title>`.

**Why `queer-guide.pages.dev` looked healthy and made this look CDN-shaped:** pages.dev deep routes hit the same branch, its shell key was simply warm. And a direct hit on `/` never enters the branch at all, which is why the homepage was always fine — an asymmetry that reads as per-route caching.

### `public/_routes.json` — assets must not invoke Pages Functions (2026-08-01)

**Pages runs Functions AHEAD of static assets by default, and Pages Functions ARE Workers billing against the same request quota.** With no `_routes.json`, every hashed chunk, font and icon invoked `functions/_middleware.ts` just to reach its pass-through — putting one cold page load at **~51 billed invocations** (1 HTML + 1 CSS + 47 JS + 2 fonts). Off Workers Paid the account has a free **100k requests/day** cap, so the whole site died after roughly **1,800 page views/day** with `429 error code: 1027` — every afternoon, self-healing at UTC midnight. `public/_routes.json` excludes the static paths, cutting that ~50×.

**Do not add `/manifest.json`, `/brand/*`, `/sitemap*.xml` or `/api/*` to `exclude`** — those are real Function routes (`functions/manifest.json.ts`, `functions/brand/`, the 15 sitemap generators, `functions/api/`) and excluding them serves the static file or a 404 instead of the generated body. `/manifest.json` is the trap: a static `public/manifest.json` also exists, so excluding it fails silently with stale content rather than an error. `exclude` wins over `include`; the two lists together cap at 100 rules.

This does not replace paying the Cloudflare bill — Workers AI, `search.`, `img.` and `extract.queer.guide` still need Workers Paid. It only stops **the site itself** from being collateral.

### Squash merges & `[skip ci]`
GitHub squash merges concatenate every branch commit message into the merge commit. If ANY squashed commit contains `[skip ci]` (e.g. the CLAUDE.md stats-sync bot commit), the resulting push to `main` skips ALL push-triggered workflows (CI, `deploy-supabase-functions`) AND the Cloudflare Pages build — nothing deploys, silently (bit us on PR #1952). If a bot commit with `[skip ci]` lands on your branch, drop/reword it before merge, or after merging recover with `workflow_dispatch` on `deploy-supabase-functions.yml` plus a follow-up commit to `main` for the Pages build.

### Migrations
- Cannot use `CONCURRENTLY` (migrations run inside transactions)
- `supabase/migrations/` is large — check for conflicts before adding new ones (see Repo stats for current count)
- NEVER reuse a 14-digit version across two files — duplicate versions break `db push` file↔history matching (34 dups renamed 2026-06-10, PR #1553)
- **Two OPEN PRs can each pass `migration-versions` and still collide — the check is per-branch, the collision is a property of the MERGE (2026-09-02, PRs #3275/#3276).** #3274 and #3275 both chose `20261119110000`; #3274 merged first, and #3275's own check had passed honestly because its branch predated #3274's file. **The failure is NOT a silent skip, which is the intuition to correct**: `db push` tries to apply the loser and dies on `duplicate key value violates unique constraint "schema_migrations_pkey"` at `INSERT INTO supabase_migrations.schema_migrations`, and the workflow ends `##[error] MERGED MIGRATIONS DID NOT APPLY`. It is loud — but only in the Actions log, and the resulting DB state reads *exactly like success*: the version IS in `schema_migrations`, so any check of the form `select count(*) ... where version='…'` returns 1. **`version` applied is not evidence YOUR migration ran — compare `name`.** Measured: version present, `name` = the other PR's, gate unchanged at 4, target rows still carrying their pre-migration stamps. Two consequences worth knowing: the deploy continues to `functions deploy` after a failed push by design, so prod can run new code against the old schema (here it printed "No edge function changes detected", so nothing shipped); and renaming the loser to a fresh version is safe **precisely because it never applied** — no history row is bound to it, so no file↔history match breaks. (Renaming an APPLIED migration is the thing that must never happen.) **CLOSED STRUCTURALLY 2026-09-02:** branch protection on `main` now sets `required_status_checks.strict=true` ("require branches to be up to date before merging"), and `migration-versions` is one of the 12 required contexts. A PR whose base has moved can no longer merge until it is updated, and that update recomputes the merge commit and re-runs the check against a tree that now contains the other PR's file — the step that did not exist before, which is why nothing re-ran when the base moved. Replayed against this incident it blocks at step 3. The cost is that every branch update re-runs all 12, including `test` (~16 min); auto-merge absorbs most of it by updating and waiting, and a merge queue is the answer if it ever thrashes. **Still worth doing by hand** when you are not relying on auto-merge: re-read remote `max(version)` immediately BEFORE merging whenever another migration PR is open — the number you picked when you branched is stale. And independently of any of this, end a data-repair migration with a `DO $$ … RAISE` that re-asserts the condition it exists to fix, which is what made this recoverable in one round instead of shipping a second false green.
- History repair: `supabase migration repair --status applied|reverted <versions>` from a checkout with all files + `supabase/.temp` link state. Pre-repair backup: `supabase_migrations.schema_migrations_backup_20260610`
- **MCP `apply_migration`'s `name` param is NOT the version.** It stamps the version from its own call timestamp and stores whatever you pass as `name` verbatim — it does NOT make the remote history match a repo filename you intended. Applying live via this tool WILL create version drift unless you immediately follow up: call `list_migrations` right after to read back the real stamped version, then `git mv` your committed file to that exact version before opening the PR (see `20260705215233_20260709100200_get_my_agenda.sql` / `20260706042931_20260709100600_fix_marketplace_brands_anon_401.sql` for the established repair-shim naming). Caused two same-day incidents on 2026-07-06 (PRs #2019/#2020, #2021/#2023) that broke `deploy-supabase-functions` with "Remote migration versions not found in local migrations directory." Also: this Supabase project has concurrent agent sessions applying migrations directly — before repairing a drift-fail, grep the target version across `supabase/migrations/` for a file someone else already added, don't assume it's yours to fix alone.
- **Drift monitor (safety net, 2026-07-26):** `.github/workflows/migration-drift-monitor.yml` runs `scripts/check-migration-drift.mjs` every 6h (+ `workflow_dispatch`) — it queries remote `schema_migrations` via the Management API and FAILS on two states: a remote version with no repo file (the exact state that makes `db push` skip silently), and — added 2026-09-02 — a version whose remote `name` disagrees with the single repo file at that version, i.e. **applied under another name**, which is what a merge-time version collision leaves behind and what no count-by-version check can see. A leading 14-digit prefix is stripped from both sides first, because the MCP repair-shim convention puts the intended version in the name; measured, that takes the disagreements from 23 to 6, so no allowlist is doing the work. The 6 survivors sit in `KNOWN_NAME_MISMATCHES`, which may only SHRINK — an entry that starts agreeing fails the check and tells you to delete it, so the list cannot rot into an allowlist nobody re-reads. This catches drift within hours regardless of push activity, closing the gap where the push-triggered check in `deploy-supabase-functions.yml` only fires when a migration is actually pushed to main (that gap let 30 versions drift undetected on 2026-07-25/26). **Remediation is automated too since 2026-09-02 — the "detection only" sentence that stood here is retired, not softened.** `.github/workflows/migration-drift-recovery.yml` runs `scripts/recover-migration-drift.mjs --write` on the same 6h cadence offset by 30 min and **opens a PR**; it never pushes to `main`, because a migration that arrived via MCP skipped review once already and committing it unreviewed skips it twice. It enumerates every orphan in ONE pass, which matters because `db push` reports only that *some* version is missing, never which or how many — so hand-recovery is iterative and each orphan hides the next, which is how four were found one at a time across hours on 2026-08-29. The manual flow above still applies to anything it skips, and the detector staying red is the backstop. Complements the pure-local `check-migration-versions.mjs` (dup/malformed versions, no remote view).

  Four properties of that script are load-bearing, each measured rather than assumed. **(1) `schema_migrations.statements` strips every trailing semicolon** — statement 1 of `20261007163200` ends `= '120s'`, its last ends `end $verify$` — so joining on newlines alone emits invalid SQL that fails only on a rebuild from zero, the one occasion an applied migration ever runs again; `STATEMENT_SEPARATOR` puts them back. **(2) Migrations are routinely multi-statement** (that same file is 4), so reading `statements[1]` silently truncates to the first — exactly what all five hand-recoveries of 2026-08-29 did, surviving only because every one of them happened to be single-statement. **(3) It never invents content**: a digest mismatch (local md5 vs a server-side digest over the same join), an empty `statements`, or an unreadable version is skipped and reported, leaving CI red. A plausible file at the right version is worse than a missing one — the missing one keeps failing until someone fixes it, the corrupted one passes every check and quietly misrepresents what ran; an empty `statements` is likewise not evidence the migration was a no-op. **(4) With no token it exits 2 rather than reporting a clean tree** — "could not look" is not "nothing found". Where the migration exists on some branch the authoring commit is preferred over reconstruction, because `statements` does not record comment headers and this repo keeps its reasoning there. The rebuild logic is exported pure and unit-tested (`src/lib/__tests__/recoverMigrationDrift.test.ts`, both guards mutation-tested) because the script cannot run without a token — otherwise CI would be the first place it ever executed, on real drift, with someone already blocked. **Still unproven: the reconstruct-and-write path has never run for real** — the first live run (2026-09-02, dispatched) found no drift, which exercises token, API and the clean exit but not the rebuild.
- **A live-applied migration left in an UNMERGED branch blocks every PR in the repo, and the two guards then deadlock (2026-08-10).** The drift check runs on the *merge commit* of every PR, so a version prod has applied whose file sits only on an unmerged branch fails `migration-versions` on **unrelated** PRs — measured: `20260810075202` was applied via MCP and stranded in draft PR #2680, which failed #2681 and #2672 as collateral for hours. `apply_migration` therefore is not "done" until the file is **merged to main**, not merely committed to a branch. The deadlock: drift demands the file at that exact version, while check 3 of `check-migration-versions.mjs` rejects a new file sorting below remote max — and renaming it upward re-breaks the file↔history match. Fixed by making the ordering rule ask remote history: a version already in `schema_migrations` is exempt, because `db push` matches by version and **skips** an applied migration instead of aborting on it. Both scripts now share one fetch (`scripts/lib/remote-migrations.mjs`) so they cannot disagree about what "applied" means, and the `migration-versions` CI step needs `SUPABASE_ACCESS_TOKEN` for it. It **fails closed** — no token or an unreachable API means no version is treated as applied and the check stays strict, saying it could not verify rather than reporting clean. So a legitimate recovery can still fail here during an API outage; that is the intended trade.

- **Shape — SOFT RE-SKIN (2026-08-17), reversing "squared corners everywhere".** The design project chose option **1b** of `Softer Drafts.dc.html` and took it through every template; Brand Guidelines §02b now reads *"26 for page-level panels, 18 for cards and fields, 12 for chips and small controls. **Nothing square.**"* The radius tokens are re-valued, not renamed: `--radius-container` 18px, `--radius-element` 12px, `--radius-badge` 9px, plus a NEW `--radius-panel` 26px for dialogs/sheets/page shells. Because 1,164 call sites already used the semantic tokens this was a **value flip, not a sweep**. `--radius-panel` and `--hairline-alpha` are declared in `@theme` **only** — deliberately absent from `tokenCatalog.ts` / `functions/_lib/branding.ts` / `branding_validate`, following the `--radius-full` precedent, which is what kept the whole re-skin free of a Supabase migration. That matters: a full `/admin/design` override already sits within a handful of keys of `branding_validate`'s **150-key ceiling**, so cataloguing either one means raising the cap in the same migration.
- **The ground layer (2026-08-18, brand update).** `body` carries a **1600×900 repeating tile of the four track colours drawn as beziers at 13% opacity**, `background-attachment: fixed` (scroll below 768px — iOS Safari repaints a fixed background every scroll frame). It is **load-bearing, not decoration**: this update returns `--background` to paper #FAFAF5, so **page and card are now the SAME colour** and a card reads because it *covers* the pattern, not because it is a lighter tone. Delete the ground and every card goes invisible — the same failure the frame-grey page was introduced to prevent on 2026-08-17, solved the other way round. `tokenContrast.test.ts` therefore no longer asserts a card/page tonal step (that would now fail on correct code); it asserts the ground exists, carries all four tracks, and that card === background by design. Text over the tile is safe — worst case is muted-on-magenta at 6.03:1, ink at 15:1. The `sanctioned ink only` e2e sweep does NOT see it: that sweep reads element `background-color` under `#root, header, main, footer`, and `body` matches none of those. Wash re-valued #F1F1E9→**#EAEADE**, well #E8E8E1→**#DDDDD1**.
- **Surfaces without cages (2026-08-17).** A container **never carries a frame**. What replaced the 3px ink cage is a pair: `--card` (paper #FAFAF5) sitting one tonal rung above `--background`, which **is no longer paper** — the page is frame-grey #EDEDE6, with wash #F1F1E9 for insets and #E8E8E1 for image wells. **`--background` moving off paper is the load-bearing fact of the whole system**: restore it to paper without also restoring the cage and every card becomes invisible, not subtler. `--border` dropped from ink to a 12%-ink divider and is now for **row rules only**; the one line allowed between surfaces is `border-border-hairline` (channels in the token, alpha in `--hairline-alpha`, because `branding_validate`'s `HSL_RE` forbids an alpha component in a value). **Three borders survive on purpose, all WCAG 1.4.11 obligations:** form controls (`border-input`, gated at 3:1 against *both* page and card), the ink ring on a track-coloured mark (`border-track-ring` — its own token, not `--foreground`, so it cannot invert when dark mode lands), and the outline of anything whose edge IS the component (outline buttons, the `DetailMasthead` status chip, alert callouts, reversed CTAs on ink bands). The de-caging codemod that deleted ~390 frames could not tell those apart and flattened 113 of them; they were restored by hand. **Check for a replacement boundary before deleting a border on an ink band**, where neither tint nor shadow registers.
- **Shadows — ONE soft elevation (2026-08-17), reversing the hard poster shadow.** `--shadow-soft` (`0 16px 40px` @6% ink) at rest, baked into `Card` itself rather than opt-in; `--shadow-soft-hover` (`0 12px 30px` @13%) + `translate(-3px,-3px)` on `.card-lift`; `--shadow-soft-lg` for dialogs/sheets/the search plate, which float over a scrim. `:active` seats back to `--shadow-soft`, **not** `none` — collapsing it drops the card flat into the page mid-tap. Shadows are authored as literal `rgba(17,17,17,α)`, never `hsl(var(--foreground)/α)`, which would flip them to a white glow in dark mode. `.card-lift-invert` was **deleted**: a card on an ink band can use no shared elevation at all (a black blur is invisible on ink, a paper blur reads as a halo), so such a tile separates by `bg-background/10` and deepens that tint on hover — see `src/pages/About.tsx`. `--shadow-hard*` are gone. Tailwind's `shadow-(md|lg|xl|2xl)` ramp **stays ESLint-banned** — soft depth being legal here does not make a second, competing ladder legal. A card **fills ink on hover or lifts — never both**. `e2e/design-system.spec.ts` now asserts the *inverse* of what it used to: a shadow at rest and **no** border. The `.plate-offset` misregistration layer and the whole PASTE-UP print layer (halftones, deckle, duotone, grain) are deleted, and as of 2026-08-19 so are the leftover class names that used to sit inert in components.
- **Gradients:** still not allowed **in JSX**. ESLint errors on `bg-gradient-to-*` in components (exception: black readability scrims over images, `from-black/NN`, and `from-background` scroll fades). `.intersection-gradient` (the four tracks blending) lives in `src/index.css` as a utility class — ESLint is scoped to `**/*.{ts,tsx}` and never parses CSS, so the one sanctioned gradient exists without weakening any JSX rule.

  **Print layer: DELETED 2026-08-19.** The last survivors of the PASTE-UP print system are gone from `src/index.css` — `.duotone-riso`, every `.halftone-*`, and `.ink-bleed` (which had zero call sites). The band-level screens, deckle, grain, misregistration and `.plate-*` classes went earlier. **The reason is the brand rules, not tidiness:** Brand Guidelines §08 says photos "run full color and unretouched. No duotones, no color washes, no gradient overlays." The `<Image treatment="riso" | "halftone">` prop, `src/lib/imageTreatment.ts` and its one call site went with them; the `image_treatment` columns on `venues` / `events` / `news_articles` stay but were non-null on **zero rows**, so nothing stored was discarded. Do not rebuild any of it. §08 Photography still contains one stale line of its own — a photo "sits inside the same 3px ink rule as every other block" — which §02b ("Ink keylines are gone from containers") supersedes; follow §02b.
- **Icons:** two tiers (2026-08-09). **`TransitIcon`** (`src/components/transit/`) is the 42-icon custom wayfinding set — stroke-only, currentColor, ROUND terminals, one station ring per icon, stroke weight bumps below 32px, never takes track colors; use it for navigation/content-type concepts, and never mix it with lucide in the same surface. **lucide-react** remains the default for UI chrome (edit/trash/chevron/…) across the ~780 importing files; `<LucideProvider strokeWidth={2.5}>` still wraps the non-admin branch of `LayoutShell` (the old butt/miter cap override was removed — round caps are the subway rule and lucide's default). Admin keeps the softer default.
- **Motion:** functional only (skeleton pulse, dialog/sheet transitions, accordion). No decorative animation (Aurora removed, ScrollReveal on hero removed). **Exception — a sanctioned queer-joy motion zone, extended 2026-07 beyond `/messages` to Groups, Dating's mutual-match reveal, and the public homepage (`/` — `src/pages/Index.tsx` + `src/components/home/*`):** these surfaces may use celebratory motion (`ReactionBurst`/`ParticleBurst` (`src/components/joy/`) on adding a reaction or saving from a home rail, `JoyBurst` confetti on a new match's first message, a group join, the dating match reveal, and the homepage born-this-week birthday tap). Homepage joy is **interaction-earned only** — never on page load, scroll, or hover. The bursts are **monochrome** (`hsl(var(--foreground))`/`--muted-foreground`/`--border` confetti pieces — the former rainbow was removed in the 2026-06-25 monochrome-strip refactor; this bullet previously described that removed rainbow treatment, which was stale) plus the bundled sticker pack in `/messages`. Every such effect is hard-gated behind `useMotionTokens().reduced || isLowEndDevice()`, `aria-hidden`, and auto-unmounts; none of it is imported by `/help`,`/safety`,`/report-*`, or Plans/Calendar (travel content stays motion-free — safety-adjacent). Do not extend this exception to other routes without updating this line. **"Motion-free" here scopes the JOY ZONE, not the functional subway keyframes** — `.track-loader`, `.station-pop`, `.station-arrive` and `.route-draw` are functional and already run across travel: `RouteFade` wraps *every* route in `.station-arrive`, `ui/loading.tsx` uses `.station-pop` app-wide, and `Button loading` renders a `TrackLoader` inside `src/components/trips/**`. `/trips/discover`'s line-draw is the same category — result-arrival feedback on an explicit user action, bounded, one-shot, never on mount, final state rendered instantly under `prefers-reduced-motion` (`src/components/trips/discover/useRouteReveal.ts`). - **Copy:** direct factual voice. No "discover/explore/unlock/curated/journey/amazing/tailored/personalized for you". Empty states: "No X yet." not metaphors.
- **Dark mode is LIVE — this line used to say the opposite and was wrong (corrected 2026-08-19).** It said dark mode was removed with the 2026-08-09 rebrand, the `.dark` block gone, `ThemeToggle` deleted and every `dark:` utility inert. None of that holds: `src/index.css` carries a full `.dark {}` token block, `ThemeToggle.tsx` exists and renders from `Footer.tsx` and `MobileNavSheet.tsx`, `ThemeProvider` applies the class and swaps the `theme-color` meta, and ~45 `dark:` utilities are load-bearing. The design agrees — `Brand Guidelines.dc.html` carries `body[data-theme="dark"]` with the same ink/paper swap and the same `--frame` / `--wash` values the repo uses. Treat dark as a supported mode: a token needs a value in BOTH blocks, and `tokenContrast.test.ts` gates each pair in both. ### Documented exceptions
- **`--destructive`** token for hard-error semantics (payment declined, pipeline failed, irreversible confirms). Reserved muted red — the ONLY chromatic color in the entire product. User-locked 2026-05-19.
- **Trip safety briefing traffic-light.** `src/components/trips/TripSafetyBriefing.tsx` retains low/moderate/high/critical risk colors. Safety > consistency for LGBTQ+ travelers in high-risk destinations. User-locked 2026-05-19.
- **Functional categorical scales** still allowlisted in `eslint.config.js`: map vector tiles, equality scores, news taxonomy, avatar gradients, submission scan flyers, trip cover gradients, content warnings, password strength meter, OAuth brand SVGs. Each is functional, not decorative.
- **City network diagrams carry all four track colors and run straight (2026-08-14).** The homepage city cards render an octilinear abstraction of each city's REAL rapid-transit network (`src/components/home/subway/CityNetwork.tsx` + generated `cityNetworkGeometry.ts`, produced by `scripts/generate-city-transit-lines.mjs` from OpenStreetMap route relations and committed — no runtime fetch, no DB column, no cron). Two rules bend, both deliberately: **(1)** all four track colors appear in one component, assigned by line LENGTH RANK (flagship = pink), because on a network map the four colors *are* the wayfinding vocabulary — "one accent per context" would make the artifact unreadable, not calmer; this is the only sanctioned four-track surface outside `.intersection-gradient`. **(2)** Segments run straight between 45° bends, so hard rule #1 ("illustrative transit lines are never straight") is now scoped to the SINGLE-line case — the fallback template line, used for cities with no rail, still obeys it. Coordinates sit on an **integer lattice**, so a diagonal step of *k* is exactly (±k, ±k) and "every bearing is a multiple of 45°" is exact arithmetic in `cityNetworkGeometry.test.ts` rather than a tolerance a rounding change could silently widen. Lines are **bare strokes, no ink casing** (user decision, 2026-08-14 — a black outline reads as a border around a shape, not as a route; border-gating still governs filled shapes, and a route line is not one). Trunk-sharing lines are separated by small INTEGER nudges whose pairwise differences are neither axis-aligned nor diagonal, so two lines can never re-converge along a heading they are allowed to run in — without them New York's R/N/F/M drew on identical pixels and only the last color was visible. Lines are ranked by length **inside a 12 km core**, not total length, or a suburban orbital leads (Madrid opened with L12/MetroSur drawn as a hook detached from the rest); relations tagged proposed/under-construction are dropped, or Paris leads with the unbuilt Grand Paris Express and Tel Aviv publishes two light-rail lines that do not exist. **Two Overpass traps, same shape — an empty 200 is never an answer.** (1) It returns **HTTP 200 with an empty element list and a `remark`** when a query times out, so a bare `res.ok` check cached "Madrid has no metro"; Madrid, Paris, Mexico City and San Francisco all lost their metros and the empties were indistinguishable from genuine absences. (2) Worse, **`overpass.osm.ch` is a SWITZERLAND-ONLY extract that returns a clean `200 {"elements":[]}` for the rest of the world with no `remark` at all** — pinned to a third of a 487-city run it cached "no network" for Essen, Dortmund, Gothenburg, Leipzig and ~450 others, and the run reported 34/487 as if that were data. Nothing in a response says "I am a regional extract", so `probeEndpoints()` now asks every endpoint a **control query the whole planet agrees on** (Berlin's U-Bahn, ≥5 relations) at startup and drops any that fails. Only planet mirrors belong in `OVERPASS_ENDPOINTS`, and the probe distinguishes BUSY (a 504 — retried with backoff) from REGIONAL (an empty 200 — condemned at once), because after a few thousand requests both mirrors 504 for a while and treating that as unhealthy aborts a run that would be fine ten minutes later. **Coverage is a population-ordered PREFIX, not a threshold** (307 cities, everything listable down to ~180k): Overpass throttles a long sweep from 2/min to 0.39/min, so the run is built to be stopped and shipped at any point. Responses are cached on disk, so extending it only costs the new tail, and `--cached-only` re-derives the committed file without fetching. A city already fetched under the old per-mode split keeps those files; a fresh one asks for all three modes in ONE request (~85% of small towns have no rail and used to pay a rail query AND a tram query to learn it — combining them was a 2.4x speedup with zero cache invalidation). Line identity is `ref || colour || name`: systems with no `ref` are named for their endpoints, so Stockport drew Manchester Metrolink's ONE line as four colours ("Rochdale - East Didsbury", "Rochdale Town Centre - East Didsbury") — no string surgery recovers identity from that, the colour does. The write guard gates on whether a run would SHRINK the committed file, never on yield rate: yield is 46% above 500k and a few percent below 100k, so a rate gate would refuse every legitimate expansion. Geometry is ODbL; the footer carries the credit.
- **Inline links underlined.** `p a, li a, td a, span a, label a` get `text-decoration: underline` in `src/index.css`. Without color difference from body text, the underline is the only cue that distinguishes a link (WCAG 1.4.1, axe `link-in-text-block`). Standalone links — nav, buttons, cards — stay un-underlined.
- **Card links are overlay siblings, never wrappers (2026-07-27, #2370).** A whole-card click target is an absolutely-positioned `LocalizedLink` rendered as the LAST child of the card's `relative` wrapper (`CardHoverEffect`), a **sibling** of `<Card>` — never an `<a>` wrapping the card. Wrapping puts the card's tag chips and its favorite / add-to-trip / check-in / share buttons inside an anchor: invalid HTML and axe `nested-interactive` (serious, WCAG 4.1.2). Canonical examples: `EventCard.tsx`, `VenueCard.tsx`, `GeoCard.tsx`, `NewsCard.tsx`. Rules when using it: the overlay needs `no-underline` (the unlayered `li a:not(.no-underline)` rule in `index.css` would otherwise force `position: relative` and collapse it) and an `aria-label` (it has no text); action buttons need `z-10` to sit above it — `FavoriteButton` and `VenueCheckInButton` take no `className`, so put it on their wrapper. Tag chips inside a card pass `linkless` to `TagChipRow` (renders `<span>`, not `<a>`); on detail pages they stay links. `<Link>` wrapping `<Button>` is the same violation — use `Button asChild` with the link inside. Guarded by `e2e/nested-interactive.spec.ts` and `expectNoNestedInteractive()` in `src/test/test-utils.tsx`.
- **Crisis & safety pages are animation-free.** `src/pages/HelpHotlines.tsx` and any future route under `/help`, `/safety`, `/report-*` must not consume Aceternity components, scroll-reveal effects, or decorative motion. Functional motion only (focus rings, dialog transitions, accordions). Protects users in crisis from cognitive overload and respects `prefers-reduced-motion` (WCAG 2.3.3). The Pattern Library (`/pattern-library` → §A11y exemption) documents the canonical static pattern.
- **Semantic radius tokens.** Always pick from the trio `rounded-container` (16px — cards, sheets, dialogs, hero blocks), `rounded-element` (8px — buttons, inputs, list rows, nested cards, image frames), `rounded-badge` (4px — chips, pills, status tags) over raw `rounded-(sm|md|lg|xl|2xl|3xl)` literals. The trio is a single point of change for the entire visual rhythm. `rounded-full` permitted for avatars/dots only; `rounded-none` for explicit flat overrides.
- **Pride map canvas — REMOVED (2026-06-25).** The former pride-spectrum overlay (`PRIDE_LAYER_COLORS` + the rainbow density-heat ramp, gated by the `pridePalette` prop) was stripped in the monochrome refactor. The `/map` canvas now uses only the **functional** categorical `LAYER_COLORS` (`src/hooks/useExploreMapData.ts`) — distinguishing layer types (venue/event/city…), the same functional map-color exception allowlisted for vector tiles — plus a monochrome black-alpha density ramp in `src/components/map/ExploreMap.tsx`. The `pridePalette` prop was renamed `mapShellMode` (it now only gates MapShell-specific UX like the empty state, not color). Chrome stays strictly monochrome.
