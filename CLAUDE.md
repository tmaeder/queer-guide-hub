# Queer Guide

LGBTQ+ travel & community platform at queer.guide

## Commands

| Task | Command |
|------|---------|
| Install | `npm install` |
| Dev | `npm run dev` (port 8080) |
| Build | `npm run build` |
| Test | `npm test` |
| Lint | `npm run lint` |
| Typecheck | `npm run typecheck` |
| Format | `npm run format` |

**Typecheck is a baseline ratchet.** `npm run typecheck` runs `scripts/typecheck-ratchet.mjs` → real `tsc -p tsconfig.app.json --noEmit`, compared against `scripts/typecheck-baseline.json`; it fails only on errors NEW per (file, TS-code). ~1.4k pre-existing errors are recorded there (a large share are Supabase client type-inference `SelectQueryError` unions, not live bugs). Fix errors rather than re-baselining; after fixing, run `npm run typecheck:baseline` to lock the improvement in. `npm run typecheck:functions` is a separate **zero-tolerance** gate (`tsconfig.functions.json`) covering `functions/` — the Cloudflare Pages edge middleware, which `tsconfig.app.json` (`"include": ["src"]`) never saw; it starts and must stay at 0 errors. Until 2026-07-29 `typecheck` was bare `tsc --noEmit` against the solution-style root tsconfig (`"files": []` + `references`) — with no `-b` that compiles **zero** files and always exits 0, so the CI gate was vacuously green for its whole life. Never "fix" errors by loosening `tsconfig.app.json`.

The scraper has its own `package.json` under `scraper/` — `cd scraper && npm install`, then `npm test` etc. there. Workers each from their own directory: `wrangler dev` / `wrangler deploy`.

**Event field backfill + vocabularies (2026-08-01):** The 40k-row `events` corpus (99% past, 36.5k scraped from the Wayback Machine — `event_sources.payload.metadata.from_wayback`) had almost every optional field empty. **The derivation logic already existed as triggers and had simply never fired on legacy rows**: `trg_events_geo_derive` (→ `derive_entity_geo_address('full')`) resolves country text → `country_id`, `city_id` → `country_id`/`city`/`country`, `cities.region_name` → `state`; `trg_events_set_currency` (→ `set_event_currency_from_country()`) fixes `currency`. The one gap is city *text* → `city_id`, so writing `city_id` is the keystone that cascades into four other columns. Two batched runners (migration `20260801135216`, crons `event_city_link` `5 3 * * *` / `event_geo_fill` `10 3 * * *`, both in `admin_automations`): `run_event_city_link` matches `(country_id, lower(cities.name)=lower(events.city))`; `run_event_geo_fill` adds city-centroid coords (stamped `field_provenance.latitude.source='derived:city_centroid'`) + `cities.timezone`, falling back to `countries.timezone` **only for single-timezone countries** (`countries.timezone` for US is `America/New_York`, so a blanket fallback would mislabel every LA event). Both stamp `enrichment_status` so unresolvable rows are tried once, not nightly. **Batch cap is load-bearing** — 6,000 rows trips the statement timeout inside `search_documents_index_events`, and a timeout is a full rollback. A third runner `run_event_timezone_fill` (migration `20260801180253`, cron `event_timezone_fill` `15 3 * * *`) covers what the city-linked path cannot: **nearest timezone-bearing city in the same country within 250 km**. That beats any state→timezone table because zone boundaries follow geography and it self-corrects for split states (TX, FL, IN, KY, MI, TN, OR, ID…). Validated against the 35,332 events whose timezone was already known: **99.71% agreement within 250 km vs 96.79% beyond**, hence the cap — uncapped it reached 2,200 km from Anchorage to Bellingham WA (no Alaskan city in `cities` carries a timezone) and would have labelled it `America/Los_Angeles`. It only fills NULLs, never overwrites; the validation incidentally showed some STORED values are wrong (Portland, Oregon events stamped `America/New_York`). Result: `city_id` 27,618→634 null, `country_id` 21,682→5, `state` 39,384→2,206, coords 36,408→659, timezone 7,058→570, currency 3,615 wrong→0, tags 29,835→4,727 untagged. **`events.country` mixes ISO2 country codes with US state codes** (`AZ`/Sedona resolved to Azerbaijan, `KY`/Murray to Cayman Islands; `CA` is genuinely split Canada/California) — repaired in `20260801142627`, which pins Whistler/Victoria/Quebec City to Canada by name because `Victoria` exists in `cities` only as Victoria, Seychelles. Vocabularies: `age_restriction` 60 spellings → `<n>+`/`all-ages` via `normalize_age_restriction` (supervision caveats resolve to all-ages **only when no explicit minimum is stated**); `accessibility_attributes` 54 values → `public.amenities` kind=`accessibility` via `normalize_event_accessibility`, **negative assertions (`not-wheelchair-accessible`, `not-step-free`, `no-accessible-restroom`) are first-class vocabulary and are never collapsed into a positive claim**; `target_groups` ~280 free-text values → 30 queer-first slugs via table-driven `normalize_event_target_groups` (extend `target_groups.aliases`, no migration needed). Both `age_restriction` and `target_groups` are exact-match filters (`useEvents.tsx`) and `target_groups` is a live search facet, so the free text was breaking them functionally. `MOAT_SYSTEM_PROMPT` in `_shared/ai-enrichment.ts` is now constrained to the closed lists so the mess cannot regrow.

**Same-name city collisions — `cities` cannot represent them (2026-08-02):** `public.cities` holds at most **one row per (name, country)**, so a corpus containing Charleston SC *and* Charleston IL can only ever match one. An "exactly one match" test therefore proves **nothing** — an unrepresentable twin looks identical to a genuinely unambiguous name. Measuring "0 ambiguous matches" was evidence the table cannot express the distinction, not evidence of safety, and the first `run_event_city_link` pass silently attached **116 events** to the wrong city (Portland ME → Portland OR, Charleston SC → Charleston IL, Springfield MO → Springfield VT, Columbia SC → Columbia MO, Wilmington NC → Wilmington DE) and then stamped each with that city's centroid coords, `state` and timezone. Ground truth for the audit is the gaycities metro slug (`event_sources.payload.metadata.gaycities_subdomain`), which spells out the state for exactly the ambiguous names (`charlestonsc`, `springfieldmo`, `portland-maine`). Migration `20260802090844` adds two guards to `run_event_city_link` — (A) `events.state` vs `cities.region_name`, (B) the metro slug's state suffix — and **blocks rather than guesses**, stamping `enrichment_status.event_city_link.blocked` + `needs_attention`: a null `city_id` is recoverable, a wrong one is not. The 122 affected rows (116 from the backfill + 6 pre-existing) are unlinked and flagged; the correct cities **do not exist in `cities` at all**, which is what made the collision invisible, so they stay unlinked until real rows exist. **`run_event_city_link` is not the only writer of `events.city_id`** — `geo-link-content` (hourly cron) resolves by name and falls back to `candidates[0]` sorted by *population descending*, i.e. it actively prefers the bigger same-name city; it re-linked a quarantined Portland ME event within the hour. The same defect class hit the venue linker: migration `20260802100455` filters events whose `venue_name` is really a city or queer-village name ("San Francisco", "Puerto Vallarta", "East Village"), which `venues` also contains — 15 of 65 `name_exact` matches were place collisions, a 23% error rate on the branch `link_event_venues` auto-applies with no review. **Rule: never resolve an entity by name alone when the reference table cannot represent the ambiguity — require a second, independent signal, and block when it disagrees.** **The news path had the same hole (guard C, 2026-08-02):** 13 of the 132 articles linked to Portland, Oregon named Maine. An article has neither a `state` column nor a metro slug, so the corroborating signal has to come from its own prose. **The writer was not the one it looked like** — 9 of the 13 never mention "Portland" in title or excerpt, so `extractGeoFromText` (which reads only those two fields) could not have produced them; all 13 sat in `news_articles.city_ids`, which only the commit path writes, and the real source was `resolveEntities` in `_shared/news-quality/entity-link.ts`, whose `passesDisambiguationGuard` returns ok immediately for every non-country type — cities had **no** guard at all. Both writers are now guarded via `proseStateContradiction()`. **The obvious rule was measured and rejected:** "any US state in the text that disagrees with `cities.region_name` blocks" fires on **873 of 9,538** US city links and is overwhelmingly correct links that merely mention another state in passing (a Seattle article referencing Indiana, a SCOTUS roundup listing five states) — it would delete ~9% of a working topical index to fix 13 rows. What separates the 13 from the 873 is that **Portland is an ambiguous name and Seattle is not**, so the burden of proof is inverted for a curated ambiguous-name set only, bringing it to **53 of 9,538 (0.55%)**. Two artifacts are load-bearing: a state whose name is inside the city's own name must be ignored (else "Kansas City, Missouri" reads every mention of Kansas as a contradiction — the largest false-positive group), and **`Washington` is excluded from the state vocabulary entirely** (state + city + everyday name for DC at once, so it false-blocked Arlington, Virginia). Bare 2-letter codes are never matched in prose — "ME", "OR", "IN", "OK" are ordinary English words — and demonyms ("Mainers") are deliberately not matched either. Cleanup `20260809163000` cleared the 53 rows from `news_article_cities` **and** `news_articles.city_ids`; clearing only the join table would let them resurrect, because the commit path unions the array (`city_ids || v_city_ids`) on every update.

**City Fields Backfill (2026-08-01):** 13 city columns were at **literally 0%** because nothing had ever written them (`climate_type`, `local_language`, `mayor`, `postal_codes`, `area_codes`, `sister_cities`, `universities`, `economy_sectors`, `cost_of_living`, `transportation_info`, `demographics`, `best_time_to_visit`, `notable_landmarks`), and `city-factual-backfill` had filled **zero fields for 36 days** while visiting ~90 cities/day. The stall was **selector starvation, not an API block**: once `never_refreshed` hit 0, `cities_due_for_refresh` collapsed to "placeholders first, lowest completeness first" and pinned itself to ~545 completeness-2 import shells whose names are region-qualified/German-localized (`Kapstadt, Südafrika`) or not cities (`Indonesien`, `—N/a`) — 2,921 log rows over 545 distinct cities, every miss logged as a bare `skipped` with no reason. **Selector v2** (`20260801133923`, ordering fixed again in `20260801140449`): content-bearing cities first, placeholder tier deleted, terminal sentinels excluded, and **`last_refreshed_at ASC NULLS FIRST` outranks `completeness_score`** — completeness is only recomputed nightly, so ordering by it re-selects a just-enriched city immediately. **`last_refreshed_at` is the selector's round-robin cursor, so it MUST be stamped on every visit** — an earlier "skip the no-op UPDATE" optimisation (to dodge the spine+profile upsert and `search_documents` HNSW churn) made unfillable cities a permanent queue head and dropped the sweep from 36/40 to 0/40 per batch. The real write saving is the terminal sentinel (`enrichment_status.<key>.state='data_unavailable'` after 3 attempts, ported from the countries engine) which removes exhausted rows from the pool; `reset_city_enrichment_state()` clears it. **`cities.wikidata_qid` + `wikipedia_title` are cached** (mirrored onto `geo_city_profiles` AND `sync_geo_spine_city()` — the drift check only compares name/slug/parent_id, so a missing profile column would never alarm); a repeat visit costs one `wbgetentities` instead of five requests, and Wikipedia is fetched **by cached sitelink title, never by `cities.name`**. `_shared/city-name-normalize.ts`: **comma-stripping alone** recovers the exonyms (`wbsearchentities` "Kapstadt" → Q5465 "Cape Town" under `language=en`); `name_en` is filled on 7 of 5,113 rows and is a dead end. **The BARE name must be searched first** — `wbsearchentities` matches labels, so "Buenos Aires, Argentina" returns only Q1537768, an obscure Córdoba town whose description also contains "Argentina", which satisfied the country check and beat the capital Q1486; Buenos Aires was published with that town's mayor. The country-qualified form is a fallback only, and a `relink` body flag re-resolves past the QID cache (otherwise a wrong QID is permanent). **`local_language` uses P37, falling back to P2936 only when it names ≤2 languages** — Wikidata fills P2936 ("language used") with minority/indigenous/historical languages, and of the 63 rows that fallback produced, every 3+-value answer was wrong (Jerusalem "Yevanic, Lishana Deni, Biblical Hebrew"; Delhi "Punjabi, Bauria, Central Tibetan") while every 1-2-value answer was right (Manila → Tagalog). Mexico City is the trap: its P37 is an unknown-value snak, so it fell through despite having an official language. **Staleness is judged against a provenance SNAPSHOT taken before the run** — `addCandidate` rewrites `field_provenance[field]` with the fresh value and runs before the write guard, so reading live provenance compares the NEW value to the OLD column and concludes a human curated it; Buenos Aires kept the wrong mayor through two relink passes while its own provenance already said "Jorge Macri". An array of all-NULLs counts as EMPTY (236 of 326 `airport_codes` rows held exactly `[null]`). ### SPA routing on Cloudflare Pages (2026-08-01)

**Three things here are load-bearing and `scripts/check-pages-routing.mjs` fails the build if any of them changes: no SPA catch-all in `public/_redirects`, no `public/404.html`, and `public/_routes.json` present.** With no `404.html` in the output, Pages' built-in fallback serves `index.html` (200) for any unmatched path and leaves static assets alone. That is the only shape that works; every alternative was measured against the real rule engine (`wrangler pages dev`) and fails:

- `/*  /index.html  200` — **silently dropped.** Pages strips `.html`/`/index` from rewrite targets, so the rule re-enters itself and the parser discards it as an infinite loop. Everything then fell through to `404.html`: `/help`, `/city/:slug` and every sitemap 404'd site-wide. Wrangler printed the warning on *every* deploy for months and nobody read it.
- `/*  /  200` — parses, but **200-rewrites outrank static-asset serving**, so `/robots.txt`, `/build-id.txt` and every hashed `/assets/**.{js,css}` are served the SPA HTML. The homepage rendered completely unstyled. (#2469, reverted in #2473.)
- `/section/*  /index.html  200` — same infinite-loop drop. `/section  /index.html  200` — 308-redirects instead of rewriting. **No rewrite whose target is `/index.html` can ever work here.**
- Status `404` is not expressible: Pages accepts only 200/301/302/303/307/308. Four `/assets/* /404.html 404` guards lived in the file for months and were rejected by the parser on every deploy.

`public/_routes.json` is shipped explicitly rather than left to wrangler. Without it wrangler generates the routing config and reads it back inside a bare `catch {}` (the `routesOutputPath` branch of `pages deploy`), which can upload the Functions bundle with no routes at all and no warning. The explicit file takes the validated branch and logs `✨ Uploading _routes.json` on every deploy, so the config is provably applied. **This was tried as a fix for the dead-Functions fault below and did NOT fix it** — keep the file (it removes a real silent-failure path), but do not mistake it for the cause.

### Pages Functions do not execute in production — CAUSE FOUND: the Workers quota

Every Pages Function 404s in production: `/sitemap*.xml`, `/api/*`, `/brand/tokens.*`, all crawler `<head>` injection and the nonce CSP. **The repo was correctly eliminated as the cause** — bundle compiles and uploads (158 KB), `_routes.json` uploaded and validated, the identical bundle serves every Function under `wrangler pages dev`, it fails on the raw `*.pages.dev` URL too, no `_worker.js`, no Node builtins, no top-level throws, and the responses are clean static 404s rather than `1101` Worker errors (never invoked, not invoked-and-crashing).

**It is the account request quota, not routing.** One command settles it — curl any Worker subdomain:

```
curl -s -o /dev/null -w '%{http_code}\n' "https://search.queer.guide/search?q=test"   # 429
curl -s https://img.queer.guide/ | head -1                                            # error code: 1027
```

`search.`, `img.` and `extract.queer.guide` all returned `429 error code: 1027` simultaneously on 2026-08-01. **Three unrelated Workers failing at once is account-level, never a code bug.** Invoice IN-72568830 is unpaid, the account is off Workers Paid, and the free **100k requests/day** cap is exhausted daily — and **Pages Functions ARE Workers billing against that same cap**, so they stop executing with it. It self-heals at UTC midnight and breaks again each afternoon. That also explains the two observations that looked most like a routing bug: it fails identically on `*.pages.dev` (same account), and it works under `wrangler pages dev` (local runtime, no quota).

**Check the Worker subdomains for 1027 BEFORE investigating Pages routing.** The repo-side elimination above cost a full session and could not have succeeded, because nothing in the repo was wrong.

Only a billing action fixes it. `public/_routes.json`'s exclude list (below) is the code-side mitigation — it cuts invocations ~50× so ordinary traffic no longer exhausts the cap — but `search.`, `img.`, `extract.` and Workers AI stay down until Workers Paid is restored. Until then `scripts/smoke-pages.sh` reports the degradation on every deploy without failing it (a known, tracked fault should not mask a new regression).

The built-in fallback answers *any* unmatched path with `index.html`, hashed-asset URLs included, so a stale bundle asking for a deleted chunk gets `200 text/html`. `functions/_middleware.ts` would turn that into a real 404 — but only while Functions run, so today `public/sw.js` is the only layer actually doing it.

### Poisoned BROWSER cache for /assets/* — per-user, no purge or deploy can fix it (2026-08-08)

`_headers` stamps `/assets/*` `immutable, max-age=31536000` **on whatever Pages serves under that path** — verified live: a nonexistent hashed URL returns the SPA shell `200 text/html` with the immutable header; mid-deploy it can be a 404. A browser that fetches a chunk during a deploy window caches that failure **for a year, in the user's own HTTP cache** — a third variant after the CDN-PoP and CORS-variant poisonings, and the only one no purge, redeploy or hash rotation can reach. A document reload (including `?__fresh=`) cannot fix it: the fresh document re-imports the same hashed URL through the poisoned cache (measured on a real user's Chrome after the #2621 deploy — 8 chunks pinned at 404, guard fired every reload, page blank forever). The ONLY escape is a per-URL `fetch(url, {cache:'reload'})`, which bypasses **and rewrites** the entry. Three layers now do this: (1) `public/sw.js` retries any suspect `/assets/*`/`/fonts/*` response with `cache:'reload'` and serves the fresh copy transparently — controlled clients never even see the failure; (2) the inline boot guard (`index.html` + the middleware-injected copy in `functions/_lib/boot-guard.ts`, kept byte-identical by `src/test/__tests__/bootGuardSync.test.ts`) heals every known asset URL **before** its `?__fresh=` reload and allows **two** gated attempts (attempt 1 can land while the window is still propagating); (3) `src/main.tsx` heals failed URLs quietly on post-boot `vite:preloadError` so a poisoned lazy-route chunk can't brick that route on every future visit (`src/utils/assetHeal.ts`). A `_headers` per-status override is not expressible, and `/assets/*` must stay excluded from Functions (`_routes.json`, quota) — client-side healing is the only available layer.

**Read wrangler's parser output.** It reports dropped `_redirects` rules — and says nothing at all about unrouted Functions — on a deploy that otherwise exits 0 and prints "Deployment complete".

**A bad `_redirects` rule outlives its revert — it poisons the CDN.** The `/  200` window above lasted ~13 minutes, but Pages answered `/assets/css/index-*.css` with `index.html` during it and `public/_headers` stamps `/assets/*` `immutable, max-age=31536000`, so Cloudflare cached the SPA shell **under the stylesheet URL for a year**. The site rendered completely unstyled for hours after the revert deployed, across three clean deploys, because reverting config does not evict a cached object and the content hash never moved. Two things to know: **(1) it is per-colo** — `smoke-pages.sh` passed from the CI runner while the same script failed from Zurich, so a green deploy proves one colo is clean and nothing more; **(2) the escape is a purge or a new URL, never a redeploy.** `expect_asset_type` in `scripts/smoke-pages.sh` now tells the two causes apart (plain URL wrong + `?cb=` right ⇒ poisoned cache; both wrong ⇒ origin broken). Hashed chunks can be rotated by changing their bytes; `/fonts`, `/icons` and `/images` cannot be rotated at all — only a purge clears those.

### Stale SPA documents on the APEX that no purge can evict (2026-08-03)

Extends the stale-document fault above with eliminations that have now cost several sessions.

**`purge_everything` fails too, not just purge-by-URL.** Measured 2026-08-03: a targeted purge of all 55 shell URLs left `/venues` and `/events` untouched, and the escalation to `{"purge_everything":true}` was accepted by the API and *also* left them untouched. Together with `cf-cache-status: DYNAMIC` alongside `age: 130273`, that definitively excludes the zone cache — there is nothing there to evict. `scripts/smoke-pages.sh` now automates the whole ladder (targeted purge → escalate → re-verify) and prints "STILL stale after purge_everything". **That message means this fault. Stop purging.**

**Diagnose in this order.** The apex-vs-pages.dev comparison comes first, because it rules out the deployment in one command:
```
curl -s https://queer.guide/venues           | grep -o 'index-[^"]*\.js'   # stale
curl -s https://queer-guide.pages.dev/venues | grep -o 'index-[^"]*\.js'   # CURRENT
```
Pages serves the current build; only the apex is stale, so no redeploy can help. `?cb=` is second and **falsely reports healthy** — it is a different cache key, so it reaches origin and tells you nothing about what users get. Third, curl a worker subdomain for `error code: 1027` (the Workers quota, which independently kills every Function daily until ~00:00Z).

`functions/_middleware.ts` DOES run on the affected routes — canonical and CSP nonce are both injected — so the request reaches our code and the middleware is not the cause. A previous session inspected the entire zone in the dashboard (Always Online, URL purge, Cache Rules, Workers Routes, Page Rules, DNS, the Pages custom domain) and ruled all of it out. **Cloudflare-side; needs support.**

**The inline self-heal guard can never fire on an already-stale document.** `index.html` and `main.tsx` reload through `?__fresh=` for exactly this case (a bare `location.reload()` re-fetches the same key, and the one-retry gate then pins the page blank forever). But the guard is an inline script, and a stale document carries the nonce from its original render while the CSP header is regenerated per request — mismatch, blocked. When Functions are quota-dead there is no nonce at all and `script-src 'self'` has no `unsafe-inline` — blocked again. The guard protects documents cached from now on; it cannot repair the ones already stuck.

**Do not "fix" this in `_middleware.ts`.** Sourcing the shell from `env.ASSETS.fetch('/')` is the obvious-looking repair and is the wrong layer, per the pages.dev evidence above. It would also risk clobbering the Function-generated HTML that `functions/news/[slug].ts` and friends legitimately return from `next()`.

### `public/_routes.json` — assets must not invoke Pages Functions (2026-08-01)

**Pages runs Functions AHEAD of static assets by default, and Pages Functions ARE Workers billing against the same request quota.** With no `_routes.json`, every hashed chunk, font and icon invoked `functions/_middleware.ts` just to reach its pass-through — putting one cold page load at **~51 billed invocations** (1 HTML + 1 CSS + 47 JS + 2 fonts). Off Workers Paid the account has a free **100k requests/day** cap, so the whole site died after roughly **1,800 page views/day** with `429 error code: 1027` — every afternoon, self-healing at UTC midnight. `public/_routes.json` excludes the static paths, cutting that ~50×.

**Do not add `/manifest.json`, `/brand/*`, `/sitemap*.xml` or `/api/*` to `exclude`** — those are real Function routes (`functions/manifest.json.ts`, `functions/brand/`, the 15 sitemap generators, `functions/api/`) and excluding them serves the static file or a 404 instead of the generated body. `/manifest.json` is the trap: a static `public/manifest.json` also exists, so excluding it fails silently with stale content rather than an error. `exclude` wins over `include`; the two lists together cap at 100 rules.

This does not replace paying the Cloudflare bill — Workers AI, `search.`, `img.` and `extract.queer.guide` still need Workers Paid. It only stops **the site itself** from being collateral.

### iCloud & Git
The repo lives in an iCloud-synced folder. `.git` objects get evicted. If git commands hang or fail, run `brctl download .git` first.

### DB Column Names (common traps)
- All entity tables use `is_featured` (boolean). The legacy `featured` column on `venues` and `events` was dropped in PR #312; codebase migrated to `is_featured` end-to-end.
- `personalities.birth_date` / `death_date` (date type, NOT `birth_year` / `death_year` int)
- `news_sources.source_type` (NOT `type`), `.last_fetched_at` (NOT `last_fetch_at`)
- `countries.code` (NOT `iso_code`)
- `events.title` (NOT `name`)

- `personalities` has NO `known_for` column — use `profession` + `lgbti_connection`

### Squash merges & `[skip ci]`
GitHub squash merges concatenate every branch commit message into the merge commit. If ANY squashed commit contains `[skip ci]` (e.g. the CLAUDE.md stats-sync bot commit), the resulting push to `main` skips ALL push-triggered workflows (CI, `deploy-supabase-functions`) AND the Cloudflare Pages build — nothing deploys, silently (bit us on PR #1952). If a bot commit with `[skip ci]` lands on your branch, drop/reword it before merge, or after merging recover with `workflow_dispatch` on `deploy-supabase-functions.yml` plus a follow-up commit to `main` for the Pages build.

### Migrations
- Cannot use `CONCURRENTLY` (migrations run inside transactions)
- `supabase/migrations/` is large — check for conflicts before adding new ones (see Repo stats for current count)
- NEVER reuse a 14-digit version across two files — duplicate versions break `db push` file↔history matching (34 dups renamed 2026-06-10, PR #1553)
- History repair: `supabase migration repair --status applied|reverted <versions>` from a checkout with all files + `supabase/.temp` link state. Pre-repair backup: `supabase_migrations.schema_migrations_backup_20260610`
- **MCP `apply_migration`'s `name` param is NOT the version.** It stamps the version from its own call timestamp and stores whatever you pass as `name` verbatim — it does NOT make the remote history match a repo filename you intended. Applying live via this tool WILL create version drift unless you immediately follow up: call `list_migrations` right after to read back the real stamped version, then `git mv` your committed file to that exact version before opening the PR (see `20260705215233_20260709100200_get_my_agenda.sql` / `20260706042931_20260709100600_fix_marketplace_brands_anon_401.sql` for the established repair-shim naming). Caused two same-day incidents on 2026-07-06 (PRs #2019/#2020, #2021/#2023) that broke `deploy-supabase-functions` with "Remote migration versions not found in local migrations directory." Also: this Supabase project has concurrent agent sessions applying migrations directly — before repairing a drift-fail, grep the target version across `supabase/migrations/` for a file someone else already added, don't assume it's yours to fix alone.
- **Drift monitor (safety net, 2026-07-26):** `.github/workflows/migration-drift-monitor.yml` runs `scripts/check-migration-drift.mjs` every 6h (+ `workflow_dispatch`) — it queries remote `schema_migrations` via the Management API and FAILS on any remote version with no repo file (the exact state that makes `db push` skip silently). This catches drift within hours regardless of push activity, closing the gap where the push-triggered check in `deploy-supabase-functions.yml` only fires when a migration is actually pushed to main (that gap let 30 versions drift undetected on 2026-07-25/26). Detection only — remediation is still the manual recover-into-a-file flow above (recover orphan SQL from `schema_migrations.statements` into a file at its exact version; never a blind `db pull`). Complements the pure-local `check-migration-versions.mjs` (dup/malformed versions, no remote view).

## Design

LGBTQ+ travelers, locals, activists, researchers, allies. Safety-first, inclusive by default, content is the hero.

- **Color — SUBWAY MAP track set (2026-08-09).** Paper base (`--background: 60 33% 97%` #FAFAF5) + ink (`--foreground: 0 0% 7%` #111; `--border` is also ink — ink borders ARE the system) plus **four SEMANTIC track colors** modelled on subway lines: `--track-pink` `330 100% 56%` (#FF1F8F), `--track-blue` `193 100% 45%` (#00B4E6), `--track-green` `136 75% 52%` (#2BE05A), `--track-yellow` `50 100% 50%` (#FFD500).
